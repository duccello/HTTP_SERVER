## Tests
The `webserv` program includes the `config file` needed to perform the tests, as well the files and directories.

This test automation has two parts: functional testing and stress suit tests.

---
### 1. Functional testing
These tests check for the functional correctness of the tests, which means, for example, get the correct error message according to the configuration set in the `config file`, the directories and static files available in the root of the server.

**Note:** during the development phase, these tests where used in the `CI` on `GitHub`.

---

### 2. Stress suite test
These are stress tests, not functional correctness tests. 

There are 2 levels of testing: stress per individual server and stress multiserver. 

For the technical requirements needed to perform the multiserver testing (multiple terminal windows), it's not automated. See more details in how perform the [manual stress](stress_manual).


## Instructions
Automated test to stress individual servers.

### Stress suite test
#### Set-up testing environment
1. `make run` to `run` the server in one terminal
2. `make stress` to `run` `siege` in another terminal

#### What it does
- Creates required test files if missing
- Executes automated stress tests using `siege`.
- Test load of multiple requests (transactions).
- Test concurrent requests.
- Limit each test in time (seconds) `-t` or in repetitions `-r`.
- Includes definitions of multiple servers to be changed manually if needed, that matches the config file: 

```
SERVER0: http://localhost:8080
SERVER1: http://localhost:9080
SERVER2: http://localhost:9090
SERVER3: http://localhost:6080
```
To test with multiple server, run manually on different terminals, one per port.

#### How to read stress test results (Siege)?

When you `run` tests with `make stress`, the tester analyzes the JSON report generated by `siege`. Here's what each key metric means:

* **`transactions` (Total Requests):** This is the total number of HTTP requests that `siege` sent and that the server managed to respond to. 
**Note:** it does not mean database transactions, they are simply *requests*.
* **`availability`:** The percentage of requests that the server responded to successfully (HTTP codes less than 400, such as `200 OK`). If your server starts throwing `500` errors or goes down, this percentage will go down. The tester requires a minimum of **99.5%** to approve the test.
* **`failed_transactions`:** The number of requests that failed (the server returned an error or simply closed the connection due to overload).

#### ❌ When is a Test considered to have failed?

It will appear as **[FAIL]** and stops testing immediately if either of these two conditions occurs:
1. **`availability`** is less than 99.5% (indicating that the server is ignoring requests or breaking down under load).
2. The number of **`failed_transactions`** is greater than zero in critical stability tests.
3. The test is sensitive to the `timeout` definition versus the time set in each test case, which needs to be coherent, if not, it's possible to have a `failed test` even when the `webserv` runs conrrectly with the stress test.
